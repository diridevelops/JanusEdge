# Research: Backtest Candle Replay

This research artifact records design decisions for the Backtest workspace. Original CandleKit package inspection and sibling downloader research informed the initial design; later decisions below supersede the per-run candle snapshot choice and reflect the implemented shared-cache, manual-import, recovery, backup, and trade-detail behavior.

## Decisions

### Random start-date selection for Backtest runs

**Decision**: Keep random selection in the existing durable preparation job. At request time, capture the previous local calendar date in the user's configured display timezone as an immutable cutoff. The worker considers starts from 2005-01-01 through the latest start whose calendar duration (1, 3, 6, or 12 months, month-end clamped, inclusive end one day earlier) ends by that cutoff. It chooses eligible years randomly without replacement and probes up to ten distinct random dates per year without replacement. Each probe downloads COMB one-minute data for the UTC date or dates overlapping the candidate's local calendar day, then filters by that day's exact replay timezone bounds. Persist the year/date state and pending candidate before probing. A provider error is terminal; an empty result advances the search. Once a hit is durably recorded, the worker persists dates, creates the one account using FR-009's label rules, and continues through the existing warm-up and preparation path.

**Rationale**: A durable worker avoids blocking the API while historical data is queried and lets the run list show `selecting_period`. Persisted cutoff and attempts make recovery deterministic with respect to the eligible window and prevent the worker from counting the same empty candidate twice after restart. The account remains absent until a candidate has been confirmed.

**Trade-off**: Ten empty probes can discard a year that has candles on unsampled dates. Exhausting the bounded year list can therefore report no usable start even if some source data exists. This is the selected bounded-search behavior. A successful start-day probe only establishes that the replay begins on a data-bearing day; later gaps and empty days remain governed by the existing coverage and readiness rules.

**Alternative considered**: Probe every date in each year until data is found. Rejected because a long sparse history could require thousands of synchronous provider calls in one worker attempt; the chosen ten-date cap bounds work per year and persists each attempt for recovery.

### COMB midpoint and volume semantics

The user selected Dukascopy COMB data represented as midpoint OHLC. Compute each open/high/low/close by averaging the corresponding BID and ASK value from the same minute. Dukascopy COMB files aggregate BID and ASK separately, so averaging the side highs/lows is an estimate and cannot reproduce exact tick-level midpoint extrema without synchronized tick data. Sum `bidVolume` and `askVolume` for the one available chart-volume value; the downloader documents these fields as quoted liquidity at the best bid/ask, not executed trade volume. Keep this meaning available in accessible chart text without a persistent visible note.

Source: [Dukascopy downloader README](https://github.com/diridevelops/dukascopy-market-data-cli#decoding-and-aggregation).

### 3. Pin shared candle sources through a metadata-only run manifest

**Decision**: Keep replay sources separate from JanusEdge's imported-tick market-data store. Cache normalized Dukascopy COMB one-minute days in a per-user shared MinIO cache, including empty dates, and store source/cache references and coverage in a metadata-only run manifest. Keep Manual HistData imports as immutable, versioned user/instrument datasets; each run pins the revision it uses. Neither source copies candle bytes into a per-run object.

**Rationale**: The existing `/market-data/ohlc` route reads candles derived from locally imported ticks and does not supply Dukascopy or HistData replay. A shared cache avoids fetching the same user/instrument/day repeatedly across runs, while a manifest or manual dataset revision preserves which source a ready run references. Cache misses use expiring per-date leases so concurrent workers do not duplicate downloads. Missing references on an old or restored run are reported, then recovered only after explicit user choice; changed Dukascopy history is disclosed while committed simulation state is retained.

The sibling package exposes the downloader catalog and aligned BID/ASK candles in memory. JanusEdge uses its combined candle API, while the application retains the simulation-specific midpoint and quoted-liquidity transform. The dependency owns shared HTTP pacing and retry behavior; JanusEdge owns the per-user cache policy and run manifest.

**Alternatives considered**: Reuse `/market-data/ohlc`. Rejected because those datasets are generated from imported tick files and are not the Dukascopy or HistData replay source. Keep a full immutable candle copy per run. Rejected because it duplicates overlapping days and multiplies storage. Download candles in the browser. Rejected because ownership, cache leases, progress, and recovery belong at the authenticated backend boundary. Duplicate the downloader implementation inside JanusEdge. Rejected because the maintained package API already supports aligned BID/ASK data.

### 4. Let CandleKit drive replay while JanusEdge enforces source- and cursor-bounded display

**Decision**: Implement CandleKit’s ReplayDataSource over the run manifest's pinned cache references or manual dataset revision, returning requested UTC-day data and available-date lists. Keep one ReplayController per active run. Send ordinary forward-bar events to each chart through incremental updates. Rebuild visible chart data from the cursor after seek or step-back. Linked Backtest trade-detail charts use the same run source and cap data at the run's furthest reached timestamp, even after rewind.

**Rationale**: CandleKit documents a day-oriented replay data source, deterministic cursor, playback controls, per-bar callbacks, and efficient updateBar handling for normal playback. A shared controller naturally preserves the specification’s one-cursor-across-tabs behavior. JanusEdge must own the session calendar and gaps. It must not initialize higher-timeframe charts with pre-aggregated bars that include candles beyond the current cursor.

Each higher-timeframe candle is aggregated from the one-minute source events seen so far, using the existing UTC-aligned, left-closed/right-open boundaries. Chart time values remain UTC epoch milliseconds. Display timezone is applied by formatting, not by shifting times before aggregation or drawing.

**Alternatives considered**: Give each chart tab an independent replay controller. Rejected because tabs could diverge. Feed full higher-timeframe history and hide bars by styling. Rejected because active-bar high, low, and close values could reveal future source candles. Let trade-detail charts show the full selected run range. Rejected because this would expose candles beyond the run's actual high-water replay progress.

Sources: [CandleKit replay documentation](https://github.com/rohanbeingsocial/candlekit-charts/blob/main/docs/replay-system.md), [CandleKit architecture](https://github.com/rohanbeingsocial/candlekit-charts/blob/main/ARCHITECTURE.md).

### 5. Use CandleKit SyncEngine for crosshair synchronization

**Decision**: Use CandleKit SyncEngine for crosshair event routing only. Convert the emitting chart’s logical index to a UTC time value and map that timestamp into the receiving chart’s logical range. Keep replay synchronization in the one shared ReplayController; panning and zooming remain local and have no sync switches.

**Rationale**: CandleKit’s SyncEngine is framework-independent and requires the host to attach chart members and route events. Different intervals have different logical spacing, so broadcasting a logical index directly would misalign crosshairs. The JanusEdge adapter preserves the app’s absolute-time synchronization contract. The selected product behavior synchronizes crosshairs while keeping each pane's horizontal range independent.

**Alternatives considered**: Broadcast logical indexes without conversion. Rejected because a position such as bar 100 on a one-minute chart does not represent the same time as bar 100 on a one-hour chart. Synchronize pan and zoom. Rejected because the clarified behavior keeps each pane's range local. Write an unrelated custom sync engine. Rejected because CandleKit handles crosshair event routing and the adapter only needs the time conversion.

Sources: [CandleKit sync contracts](https://github.com/rohanbeingsocial/candlekit-charts/blob/main/src/sync/types.ts), [CandleKit architecture](https://github.com/rohanbeingsocial/candlekit-charts/blob/main/ARCHITECTURE.md).

### 6. Persist CandleKit drawings through JanusEdge’s authenticated API

**Decision**: Use CandleKit DrawingController and DrawingEngine for live state and toolbar behavior. Load and save the serialized export/import payload through an authenticated API document keyed by user, run, and timeframe. Do not use the built-in local storage key as the durable source of truth.

**Rationale**: CandleKit documents DrawingEngine export/import and drawing-change notifications. Its custom key-value store is synchronous, while JanusEdge API writes are asynchronous. An app adapter can hydrate before enabling edits and debounce backend writes after changes. This keeps drawing state in the same per-user context as the run and allows it to survive browser reloads and user devices.

The inspected 0.1.0 artifact exposes drawing anchors and DrawingEngine import/export but no replay-cursor visibility behavior. Apply the specified anchor-only filter and do not add drawing creation/edit-time history. This fallback means a drawing created later but anchored entirely in the past may remain visible after rewind, an accepted v1 trade-off.

**Alternatives considered**: Use CandleKit localStorage as the only persistence. Rejected because it is browser-local and does not follow authenticated user/run ownership. Pass JanusEdge’s asynchronous API directly as CandleKit’s KVStore. Rejected because the documented KVStore contract is synchronous. Keep drawings only in memory. Rejected because leaving and reopening a replay would lose the drawing state.

Sources: [CandleKit drawing guide](https://github.com/rohanbeingsocial/candlekit-charts/blob/main/docs/drawing-tools.md), [CandleKit drawing persistence interface](https://github.com/rohanbeingsocial/candlekit-charts/blob/main/src/drawing/persistence.ts), [CandleKit architecture](https://github.com/rohanbeingsocial/candlekit-charts/blob/main/ARCHITECTURE.md).

### 8. Persist preparation jobs and recover them through MongoDB leases

**Decision**: Run preparation and cache recovery in a worker process separate from the Flask API. Store durable job state in MongoDB, claim work with atomic expiring leases, and checkpoint completed UTC-date outcomes and shared-cache references. Keep the worker as a dedicated Docker Compose service and do not add an external queue service for v1.

**Rationale**: MongoDB job state survives API and worker restarts and uses infrastructure already required by JanusEdge. A separate process lets an API restart occur without interrupting active downloads. If the worker itself stops, an expired lease permits another instance to reclaim work. Per-date cache entries and checkpoints limit recovery to missing or incomplete dates; concurrent runs share the same cache service.

**Alternatives considered**: Run downloads in the request process or start an in-memory background thread. Rejected because process restart loses active work and queue state. Add Redis or another broker. Rejected for v1 because durable job state and atomic claim operations can use the existing MongoDB deployment without another service.

Sources: [sibling downloader instrument catalog API](../../../dukascopy-market-data-cli/src/dukascopy_market_data/instruments.py), [sibling downloader per-day API](../../../dukascopy-market-data-cli/src/dukascopy_market_data/candles.py).

Rejected because panes can be panned independently. Synchronize pan and zoom across panes. Rejected because the chart interaction contract keeps each pane's viewport local. ### 11. Delete a run through a durable, owner-scoped cleanup state

**Decision**: Require confirmation before permanent deletion. Mark the owned run `deleting` as a temporary durable cleanup marker, immediately stop replay, and let the existing worker resume cleanup after restarts. Hiding the run/account/trades from queries is only an interim pending state. Fence preparation publication and all replay/workspace/drawing/simulation writes once deletion starts. Physically remove every trade linked through the run's one-to-one account and all trade-owned dependent records/files using the existing trade cleanup path; remove run-owned MongoDB records, cache manifest references, simulation state, workspace/drawings, account and run record. Shared Dukascopy cache and all manual dataset revisions/objects remain. Only the completed run-owned purge counts as deletion. Repeated requests and cleanup passes are idempotent. Completed runs are deletable under the same cascade.

**Rationale**: A run may be preparing while the worker owns a lease, or have in-flight simulation operations, and its staged or final candle objects live outside MongoDB. A durable lifecycle marker fences late writes and allows interrupted cleanup to resume. The dedicated account's `backtest_run_id` and each trade's `trade_account_id` provide a narrow cascade boundary that preserves other runs and Real records. Reusing the existing trade deletion path avoids leaving trade-owned media or other dependent records behind.

**Alternatives considered**: Delete all resources synchronously in the HTTP request. Rejected because a process or object-store failure can interrupt the cascade, and an in-flight preparation worker still needs a cancellation fence. Introduce a second standalone deletion queue. Rejected because the run's durable `deleting` status already serves as the work marker and avoids duplicate lifecycle state. Soft-delete with a restore action. Rejected because the requested behavior is permanent removal of the run, account, and linked trades.

Sources: [`BacktestRun` ownership and worker cleanup](../../backend/app/backtests/repository.py), [preparation-worker terminal cleanup](../../backend/app/backtests/worker.py), [trade deletion cascade](../../backend/app/trades/service.py).

### 11. Keep user-requested chart context outside the replay window

### 12. Add Blind mode as a rendered-UI layer over random runs

**Decision**: Blind mode is an immutable per-run flag, unchecked by default, that requires random period selection. The create request adds `blind_mode: true` only when selected; omission preserves existing manual and random request shapes. The browser hides complete dates and raw prices from blind-run lists, details, notices, account labels, chart ticks, tooltips, deletion dialogs, and price-coordinate displays, while MongoDB, MinIO, and existing API responses retain canonical timestamps and prices. Warm-up context and every chart interval use the same ratio `100 × P / referencePrice`. Storing the run flag and reference gives Journal one authoritative source for its display rule. The user chose UI masking over API redaction.

**Alternatives considered**: Redact dates/prices from API responses. Rejected because the accepted scope is rendered-UI masking and existing replay calculations still consume canonical data. Anchor at the first warm-up candle. Rejected because the selected replay period's first available price must define 100. Reject negative reference prices. Rejected because the user chose to apply the specified formula even when its direction reverses.

### 13. Serialize simulation mutations with a recoverable run-scoped operation journal

**Decision**: Keep only bounded simulation control fields on the existing BacktestRun document: replay cursor, monotonic operation sequence/revision, reset generation, whether an order has been accepted in that generation, completion state, and one pending operation id. This lets the existing run-level compare-and-swap atomically commit cursor, sequence, and `complete` status. Store each full idempotent operation, result, order, fill, position, and applied cost snapshot as a separate record rather than an unbounded run-document array. Order, position, and cost-profile state is versioned; readers select the latest version at or below the committed sequence and current generation, while fills remain append-only. Every cursor move and submit/cancel/cost/advance/reset command supplies an idempotency key scoped to authenticated user/run. Persist operation intent and deterministic effects before advancing the run's committed sequence. Reset atomically advances the generation so old state becomes invisible, then physically purges that generation while the pending-operation gate blocks new writes. A request handler or recovery worker resumes a pending operation after restart.

**Rationale**: A user can issue an order while replay is moving, and a retry after a timeout must not create duplicate fills or trades. The repository already uses optimistic revisions on run replay position/workspace and has durable leases for worker recovery. Putting only bounded control metadata on the run document preserves its existing role as cursor authority while making cursor, completion, and operation-sequence advancement one atomic MongoDB document update. Versioned state leaves the last committed projection readable while a new operation's effects are being staged. The Compose MongoDB is standalone, so relying on multi-document transactions would fail in the supported local deployment. A CAS gate plus deterministic journal and committed-sequence visibility makes ordering explicit and recovery possible without adding a new queue service. Forward seek must run each source candle through the same processor as play/step, otherwise it could skip a stop, target, or pending-entry fill.

**Alternatives considered**: Keep simulation state only in React. Rejected because browser state is not durable. Store every simulation entity or event in growing arrays on the run document. Rejected because run-document size would grow without bound. Keep the complete simulation control in a separate document. Rejected because it duplicates cursor/status authority and makes cursor plus `complete` commit cross-document. Use separate independent order and cursor endpoints with no shared revision. Rejected because races could reorder entry eligibility and candle processing. Require Mongo replica-set transactions. Rejected because the checked-in Compose service is standalone and v1 should work there. Use a general-purpose message broker. Rejected because one run-scoped ordered mutation stream can use existing MongoDB infrastructure and recovery patterns.

### 14. Keep open exposure separate and publish only fully closed Backtest trades

**Decision**: Persist pending/working orders and open positions in dedicated Backtest simulation records. Reserve a conventional Trade id when each position is created and put that id on each per-position allocation stored as an extended existing `Execution`, alongside Backtest run/order/generation/sequence, applied cost, and event-level quote-to-USD metadata. Do not insert the Trade document until the position closes, so it cannot appear open in Journal/analytics. This lets one opposing order reduce multiple FIFO positions and open an excess reverse position without linking one Execution to multiple Trades. Freeze instrument type, base/quote currencies, pip size, price precision, and contract size from the current JanusEdge mapping in the run record. When a position is fully closed, create the existing closed `Trade` exactly once under the run’s dedicated Backtest account, using the reserved id and linked allocation executions, aggregate native quote-currency and USD gross/net P&L, initial risk, costs, and blind-run linkage. Tag the Trade with run, reset generation, and committing operation sequence; Backtest Journal and analytics consumers expose it only when that generation is current and its operation sequence is committed. Extend Backtest trade detail calculations to use the event-level execution rates for multi-exit native/USD histories instead of the Trade model's single scalar rate. Keep open positions and working orders in the Backtest replay UI. Never use the Real-only manual POST /trades path.

**Rationale**: Existing analytics consistently filter to closed trades, while creating an open Trade early risks surfacing it in Journal and APIs that are not designed for simulation lifecycle changes. The current manual route is Real-workspace guarded and takes a closed-trade payload, so it is not a valid Backtest order API. Creating the conventional Trade only on full closure reuses mature account-scoped analytics and deletion behavior while leaving open simulation state explicit and run-owned. The existing Trade model's one `quote_to_usd_rate` cannot accurately represent multiple exits at different FX rates; storing each fill's event rate and adapting Backtest trade-detail calculations preserves both the required event-level conversion and aggregate USD metrics. The sequence/generation filter lets Trade/Execution documents be safely staged before the run's single-document commit without leaking a partial operation into existing trade surfaces.

**Alternatives considered**: Reuse manual trade creation for entry and update Trade status through the simulation. Rejected because it is guarded to Real mode and its payload requires entry and exit data together. Expose open Trade documents and adapt every existing analytics consumer. Rejected because that broadens the feature and creates leakage risk. Keep closed simulation results only in a new analytics store. Rejected because it duplicates the existing Trade analytics contract without need.

### 15. Resolve forex quote-to-USD rates from immutable timestamped conversion data

**Decision**: Preserve native P&L in the traded pair's quote currency. For USD-quoted instruments, use a rate of 1 USD per USD quote unit. For non-USD Dukascopy runs, store direct, inverse, or configured shortest-route conversion candle references in the run manifest; for manual imports, use the configured USD-per-quote-unit fallback only when eligible historical conversion data is unavailable. At each entry or exit event, use the latest completed conversion candle whose close is no later than the event timestamp. Since OHLC-triggered intrabar fills do not have a recoverable sub-minute time, timestamp them at the triggering candle's opening instant; timestamp a forced final close at the candle's close. If no historical observation or valid manual fallback exists, fail the affected operation rather than inventing a rate. V1 defines no separate maximum age for the latest prior completed conversion candle.

**Rationale**: The existing trade model preserves native quote-currency P&L and defines `quote_to_usd_rate` as USD per one unit of quote currency, but its existing helper accepts only a supplied scalar; no historical rate resolver was found. A timestamped series keeps USD P&L and initial risk reproducible and avoids look-ahead from the still-forming conversion candle. Deriving USDJPY, USDCHF, and USDCAD rates from inverse prices is possible when their immutable series are part of the run. Crosses without a supported conversion path need explicit preflight failure rather than misleading USD analytics. Using the trigger candle's opening timestamp for wick-based fills is a conservative, deterministic as-of rule given the absence of tick chronology.

**Alternatives considered**: Reuse the current mutable market-data OHLC store. Rejected because it is not guaranteed to exist for a run and can change after replay. Use one scalar rate for every event. Rejected because it cannot represent historical variation. Timestamp OHLC-triggered exits at an inferred tick position inside a one-minute bar. Rejected because OHLC cannot recover that chronology. Silently assume 1 for all symbols. Rejected because it corrupts USD values for non-USD quotes. Fetch conversions on demand during simulation. Rejected because provider changes/errors would make replay nondeterministic; conversion data should be pinned by manifest references.

### 16. Require a complete, previewed bracket on every entry

**Decision**: Every market or limit entry carries both a stop-loss and take-profit. The entry panel is a collapsible sibling to the chart workspace; its draft overlay is transient UI state rather than a persisted user drawing. A new preview anchors at the current revealed close. It converts the current USD risk budget to a pip distance by dividing by the instrument's USD pip value for one standard lot, using frozen pip/contract metadata and the latest completed quote-to-USD rate no later than the current candle close; multiply by pip size for the price offset. The initial target is exactly 1R from entry (target distance equals stop distance). The preview displays quantity, projected USD risk, and risk/reward and requires valid long/short ordering before Place order. With auto-sizing enabled, lots are recalculated from the current stop distance, instrument metadata, as-of conversion, and modeled costs whenever entry or stop moves; with it disabled, the user enters lots. A limit preview can be translated as a whole, preserving its entry-to-protection offsets, and its stop and target can then be moved independently. A market preview pins entry to the current revealed candle close; only its stop and target move independently. Actual market execution continues at the next eligible candle open. User-selected limits are eligible only on future candles and fill at exactly the submitted limit price only when the candle's high-low range reaches it. Opening through the limit without range touch leaves the order pending; a wick that later reaches the price fills at the exact limit. Take-profit limits use the same rule. Configured spread, slippage, and commission are accounted separately without changing a limit's recorded fill price. Working entry orders remain immutable after submission; users may cancel and resubmit. After fill, the user may modify either or both protection levels through the ordered simulation operation gate; the new levels become eligible on the next unrevealed candle and the original risk/R-analysis basis stays fixed. A changed stop associates an idempotently ensured `stop-moved` tag with the position, creating it in General if absent, then carries it to the closed Journal Trade; target-only changes do not add the tag.

**Rationale**: Keeping draft overlays out of saved DrawingEngine documents avoids leaking unsubmitted order levels into chart annotation persistence. Requiring both protection orders before submission makes the submitted risk visible and gives each created position a complete OCO bracket. Converting the percentage budget to pips at a one-standard-lot reference yields a deterministic default stop distance without assuming a manually selected lot size; auto-sizing then adjusts the actual lots to the selected stop and modeled costs. Separating market preview reference from market execution preserves the requested visual price anchor without changing the established no-look-ahead fill rule.

**Alternatives considered**: Persist the preview through the normal chart drawing API. Rejected because an unsubmitted order would then appear as a saved user annotation. Use a fixed pip stop independent of account risk. Rejected because it would not make the initial stop distance reflect the current-balance risk budget and instrument pip value.

### 17. Add run-level balance and percentage risk with optional automatic sizing

**Decision**: Run creation accepts an initial USD balance and a risk percentage of current balance, defaulting to USD 10,000 and 1%. The USD risk budget is current balance × Risk% / 100. The default stop distance in pips is that budget divided by the instrument's USD pip value for one standard lot; frozen pip size converts pips to price. The order panel has an auto-size checkbox, checked by default. With auto-sizing enabled, derive entry lots from the per-order risk budget, selected entry-to-stop distance, frozen contract/pip metadata, event-appropriate quote-to-USD rate, and active cost profile, then round down to the 0.001-lot increment so the planned loss does not exceed budget. Recalculate preview lots as entry or stop changes. If minimum tradable size would exceed the budget, block submission and explain why. With auto-sizing disabled, accept a manual lot amount and still show projected dollar risk and percent. Record selected sizing mode, computed/entered lots, risk percent, and risk budget on each entry. The run retains starting balance and risk settings across reset; current balance is the initial balance plus committed net cash effect of fills, with each execution cost counted once, partial exits reflected as committed, and unrealized P&L excluded.

**Rationale**: A risk percentage and current balance provide a consistent per-entry dollar budget independent of the instrument's price scale. Converting that amount to pips at a one-standard-lot reference establishes a deterministic default bracket distance; auto-size then converts the budget back to lots using the selected stop distance, immutable pair metadata, FX series, and cost profile. Manual sizing remains available for users who want direct quantity control. Rounding down avoids exceeding the stated budget due to the required lot granularity.

**Alternatives considered**: Use initial balance for every risk calculation. Rejected because the requested Risk% is a percentage of current balance. Require manual lots for every order. Rejected because the panel is intended to calculate the lot size by default while preserving a checkbox for manual sizing.

### 18. Close a position manually at the current revealed candle close

**Decision**: A manual close acts on one open position and exits its full remaining quantity at the close of the currently revealed cursor candle, applying the active costs and as-of currency rate. It does not advance the replay cursor. The close execution and cancellation of the position's stop-loss and take-profit orders commit together under the simulation operation gate. Its event timestamp is the candle close, unlike wick/gap-triggered fills that use the candle opening timestamp.

**Rationale**: The user explicitly selected the current candle close for manual closure. That close is already revealed, so it can be used deterministically without inspecting a future candle; atomically removing both OCO children prevents a closed position from retaining live protection.

**Alternatives considered**: Execute the manual close at the next candle open to match market-entry timing. Rejected because the user selected the currently revealed candle close for this action.

### 19. Render chart controls for each filled position

**Decision**: Derive one indicator set per open BacktestPosition in every chart pane for the run, keyed by its stable position id. Show the fixed filled-entry line and price, remaining quantity, unrealized USD P&L marked at the latest revealed close before hypothetical exit costs, and current stop-loss and take-profit lines and prices; keep the entry line read-only. The unrealized P&L uses frozen instrument metadata and the latest completed quote-to-USD rate no later than the mark candle close; it is display-only. Let the user drag either protection independently. Disable BE when the current revealed close has crossed the entry. An X action submits the existing per-position manual close at the current revealed close and atomically cancels its linked protection. Apply Blind-mode normalized price rendering.

**Rationale**: A position aggregates same-direction entries while preserving each entry as a distinct execution. Its combined quantity and weighted entry share one protection bracket and one eventual Journal trade; opposing entries still reduce positions FIFO. Position-scoped controls derive from committed state, so merging executions does not merge unrelated positions or weaken operation ordering.

**Alternatives considered**: Persist these indicators as ordinary chart drawings. Rejected because they represent live simulation state, not user annotations, and can become stale after order processing or reset. Treat each same-direction entry as an independent position. Rejected because a scale-in is one open exposure/trade and must keep one bracket. Add special BE/close backend endpoints. Rejected because the existing position-specific protection and close operations already implement the required semantics.

### 20. Import HistData as a versioned manual replay source

### 21. Keep cache recovery explicit and source-aware

### 23. Give the downloader ownership of request pacing and combined-candle transport

### 24. Scale same-direction entries into the existing position

**Decision**: When an entry fills, attach a same-direction fill on the same instrument to the oldest open position. Add the fill as another execution, recompute weighted entry/reference, quantity, risk, and costs, retain the existing stop/target, and resize their orders. If no position remains open at fill time, create a new position with that order's bracket. Opposing fills retain FIFO scale-out and reversal handling.

**Rationale**: Matching on fill time handles pending entries correctly: they join only exposure that is still open when execution occurs. Keeping the protective bracket stable avoids silently changing an existing trade's stop/target when size increases.

### 25. Bound linked trade charts by replay progress and keep transport accessible

**Rationale**: Historical run bounds can exceed the replayed range, so plotting the full run would reveal unreached price action. High-water capping retains useful history after rewind without leaking future bars; keyboard actions mirror visible controls without intercepting text editing.
