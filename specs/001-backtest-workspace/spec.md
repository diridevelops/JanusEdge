# Feature Specification: Backtest Replay and Simulated Trading

**Feature Branch**: [001-backtest-workspace]

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "Add a Backtest workspace in JanusEdge, separate from Real mode. Download one-minute historical candles for one instrument; let the chart display a selected timeframe whose active bar updates as each underlying one-minute candle is replayed. Create one Backtest account per run. Keep real trades and backtest activity separate. Let the user manually practice trades during historical replay and review the resulting closed trades and metrics." Follow-up direction: use a dockable chart-tab workspace like the supplied screenshots and CandleKit workspace example, with tabs that can be created, moved, reordered, and split. Add a chart follow mode that keeps replaying panes on the latest revealed candle, with a return-to-latest control when a pane is panned away. Add a confirmed permanent delete action for a run that also removes its dedicated Backtest account and associated trades. Each run also loads one month of available data before the selected replay start as chart context, while replay itself starts on the selected date.

## Clarifications

### Session 2026-09-24

- Q: When selecting the start and end dates for a backtest, should those calendar dates be interpreted in UTC, your configured display timezone, or the instrument’s market timezone? → A: Configured display timezone.
- Q: When a user leaves a replay and later returns, should it reopen at that run’s last candle position, including after an app reload? → A: Save position per run across navigation and reloads.
- Q: What should the automatically created Backtest account show as its label in the Trades account selector? → A: Auto-label with instrument and date range; add a unique suffix if needed.
- Q: If a user seeks to another timestamp while playback is running, should playback continue from the new position or pause there? → A: Always pause after seeking.
- Q: Should a v1 Backtest run allow any date range for which Dukascopy has one-minute data, or should it enforce a maximum range? → A: Maximum one year per run.
- Q: How should the Backtest workspace organize the previous-run list and active replay? → A: Run list page, then a separate replay detail page.
- Q: Should the run list include runs that are still preparing or failed, and what should happen when the user selects one? → A: Show ready and preparing runs; immediately delete failed runs rather than retaining them.
- Q: If a request completes successfully but finds no candles in the selected date range, should that run be deleted like a failed run or kept as a “No data” entry? → A: Show no-data message, then remove run and account.
- Q: Should replay controls include a one-candle step-back button as well as the existing forward-step button? → A: Add step-back; hide later candles again.
- Q: What should happen when a user selects a run that is still preparing? → A: Keep it in the list with inline progress; do not open a detail.

### Session 2026-09-26

- Q: How should the selected chart timeframe advance from the one-minute replay feed? → A: Each replayed one-minute candle updates the active chart candle; a five-minute bar updates five times before closing, and playback speed is measured in one-minute candles per second.
- Q: Which chart intervals should users be able to choose when replaying the fixed one-minute data? → A: 1m, 5m, 15m, 30m, 1h, 4h, 1d, and custom whole-minute intervals.
- Q: What limit should custom whole-minute chart intervals have? → A: Cap custom intervals at 1,440 minutes (one day).
- Q: Should chart bars be grouped on the configured display timezone's clock or on UTC clock boundaries? → A: Use the same deterministic candle grouping as JanusEdge's existing chart: UTC-aligned intervals that include their start and exclude their end; display timezone affects timestamp presentation, not candle membership.
- Q: How should multiple chart tabs share one replay? → A: Tabs show the same run and instrument at their own timeframes and always share one replay position; replay synchronization cannot be disabled.
- Q: How should chart interactions behave across chart tabs? → A: Replay position is always shared. Crosshair synchronization is enabled by default; horizontal panning and zooming remain local to each pane.
- Q: Which chart synchronization controls should appear? → A: Do not show a Chart sync section; keep crosshair synchronization enabled without a visible settings section.
- Q: What should the initial and rearrangeable chart workspace look like? → A: Start each new run with one chart pane. Use a dockable tab workspace where chart tabs can be created, moved, reordered, and split into panes; keep the run's single shared replay position.
- Q: What drawing behavior should v1 use for tool selection, persistence, deletion, and stepping backward? → A: Use the standard drawing tools; persist by user, run, and timeframe across reloads; save edits and deletions; preserve replay-aware drawing visibility if the pinned CandleKit artifact provides it, otherwise hide drawings by time anchor only, never drawing creation or edit time.
- Q: How should the one-year run limit be applied to selected calendar dates? → A: Start and end dates are inclusive in the configured display timezone; the end date is before the start date's one-year anniversary. For a February 29 start, the latest permitted end date is February 28 of the following year.
- Q: What should users see during preparation and after gaps or errors? → A: Show progress stages and a percentage when measurable; after no-data or failure cleanup, show a dismissible result with the instrument, range, and next action; report fully empty dates and summarize partial gaps; do not synthesize candles.
- Q: How should custom interval input and cross-chart synchronization work at edge cases? → A: Show standard timeframes in a dropdown followed by a Custom option for whole minutes from 1 through 1,440; reject invalid custom intervals with an inline error and keep the last valid interval; retain each tab's interval across reloads; synchronize crosshairs to the same UTC time using the nearest available candle at or before it, while keeping pan and zoom local to each pane.
- Q: How many chart tabs should v1 support at once? → A: Do not enforce a fixed maximum number of chart tabs.
- Q: Should v1 add a chart-tab capacity or rendering-performance target beyond the specified playback speeds? → A: No additional capacity limit or performance target for now.
- Q: Where does the supported-instrument list come from? → A: Use the current catalog exposed by the pinned Dukascopy downloader dependency; the backend validates submitted instruments against that catalog.
- Q: How should preparation work survive an API backend restart? → A: Use a durable worker and persisted preparation jobs so interrupted work can resume without creating a duplicate run or account.
- Q: How often should the run list refresh preparation status? → A: Poll the run list every five seconds while at least one run is preparing.
- Q: What replay cursor should a newly ready run receive? → A: Persist the first available source candle in the user-selected replay period; any earlier warm-up candles are chart context only.
- Q: Which replay controls should the detail page use? → A: Use CandleKit ReplayControls; add a JanusEdge wrapper only for the speed selector if the component does not offer the required speeds.
- Q: Which Dukascopy quote series should the chart use? → A: Use the COMB BID/ASK series and display component-wise midpoint OHLC.

### Session 2026-09-28

- Q: Should blind mode also add Backtest trade entry and persistence now? → A: At that point, keep trade recording deferred and specify the future Journal display. Superseded by the 2026-09-29 clarification adding manual simulated trading and persistence during replay, with blind-run display rules retained.
- Q: Should blind-mode dates and prices be removed from API responses? → A: Apply masking in rendered UI only; retain the actual data for replay and storage.
- Q: Which price anchors the normalized chart? → A: Use the open of the first available candle in the selected replay period, excluding warm-up candles.
- Q: How should a negative reference price be handled? → A: Apply the specified ratio formula even though a negative reference reverses the normalized price direction.
- Q: What should the future Journal list show for a blind-run trade? → A: Show weekday and time plus normalized entry and exit prices; hide the complete date and raw prices.

### Session 2026-09-29

- Q: What is the purpose of simulated trading? → A: Manual discretionary practice while a historical replay runs, not automated strategy backtesting.
- Q: What historical data is in scope? → A: Reuse the current single-instrument, completed one-minute candle replay; tick and order-book replay are deferred.
- Q: Which clock controls simulated orders? → A: The backend is authoritative for replay position and order processing.
- Q: At what price does a market order fill, and may a new order use the candle already revealed? → A: Superseded on 2026-09-30; see the updated market-entry rule below.
- Q: How do limit and stop entries trigger? → A: Superseded on 2026-09-30; v1 entries are market or limit, and protective stop-market orders trigger under the future-candle wick/gap rules.
- Q: What protection is required? → A: Superseded on 2026-09-30; every submitted entry requires both stop-loss and take-profit, linked OCO after fill.
- Q: How are multiple simulated positions handled? → A: Multiple orders and positions are allowed; opposite-side fills reduce the oldest open exposure first and open a reverse position with any remainder.
- Q: How is size selected? → A: Superseded on 2026-09-30; each run has starting balance/risk inputs, auto-sizing defaults on with manual lot entry available via checkbox, and margin modeling remains out of scope.
- Q: How are execution costs represented? → A: A per-run profile supports total spread in pips, slippage per fill in pips, and commission per lot per side; unset or zero costs are disclosed as excluded.
- Q: How should trade results use currencies and analytics? → A: Preserve native quote-currency P&L, resolve historical quote-to-USD conversion at each exit for supported pairs, and expose the existing Real trade metrics for the run account.
- Q: How should simulated state survive navigation and replay reset? → A: Persist simulation state per run in MongoDB. Reset requires explicit confirmation and clears that run's simulated orders, positions, and trades; replay cannot move backward after simulation activity until reset.
- Q: What happens when replay ends? → A: Cancel pending orders and close any open exposure at the final replay candle.

### Session 2026-09-30

- Q: What protection is required for submitted entries? → A: Both stop-loss and take-profit are mandatory on every entry, linked OCO after fill.
- Q: Which entry types and chart controls are required? → A: Market and Limit only. Use a collapsible panel to the right of the charts and a transient bracket preview; Limit moves as a group, while market entry is fixed at the current candle close. Stop and target can each move independently. Shorts reverse the long bracket orientation.
- Q: How is position size selected? → A: Run creation includes initial balance (USD 10,000 default) and Risk% (1% default). An order-panel auto-size checkbox is on by default; when off, manual lot entry is available.
- Q: How does Risk% determine the initial stop distance? → A: Convert the USD risk budget represented by Risk% of current balance into pips for the selected instrument. For a determinate default price distance, the plan uses the instrument's USD pip value for one standard lot as the conversion basis; auto-sizing then calculates actual lots from the selected stop distance.
- Q: What is the initial reward-to-risk preset? → A: 1R; the target distance initially equals the stop distance.
- Q: How does manual closure work? → A: Close the full remaining position at the currently revealed candle close, and cancel both linked protective orders in the same operation.
- Q: What price fills a limit order? → A: Exactly the submitted limit price when an eligible future candle's high-low range reaches it, with no price improvement; an opening gap through the price alone does not fill the order.
- Q: Can protection be changed after entry fill? → A: Yes. Stop-loss and take-profit can be moved on an open position. The original initial risk remains fixed; a changed stop adds the `stop-moved` Journal tag, created in the General category if the user's tag does not already exist.

- Q: When does a market entry submitted at the replay cursor execute? → A: It waits for the next available unrevealed one-minute candle and fills at that candle's open; it cannot use already revealed candle data. Protective orders become eligible only after the entry-fill candle has been fully processed.
- Q: Can an opening gap alone fill a limit order when a future candle's high-low range never reaches its price? → A: No; a limit entry or take-profit fills at its exact submitted price only when an eligible future candle's range reaches that price.

## User Scenarios & Testing

### User Story 1 - Keep Real and Backtest activity separate (Priority: P1)

As a trader, I want separate Real and Backtest workspaces so that existing trading records remain separate from historical market replay.

**Why this priority**: Users must be able to trust the data shown in the existing journal and the new replay workspace.

**Independent Test**: View the app in both modes and verify that the Real workspace has no Backtest runs or accounts, while the Backtest workspace shows its runs and no real trades.

**Acceptance Scenarios**:

1. **Given** the user is in Real mode, **When** they view trades, accounts, or trade-based reports, **Then** only real activity is shown and no Backtest runs or accounts are shown.
2. **Given** the user is in Backtest mode, **When** they view trade-facing sections, **Then** no Real trades are shown and sections without Backtest trade data display an appropriate empty state.
3. **Given** the user switches modes or reloads the app, **When** they return to a workspace, **Then** its current mode is clear and saved runs remain available in Backtest.
4. **Given** the user is in Backtest mode, **When** they look for trade import or Real-style manual trade creation, **Then** those actions are unavailable; simulated order entry is available only inside a ready replay, and existing Real actions remain available in Real mode.

### User Story 2 - Prepare a one-instrument replay (Priority: P1)

As a trader, I want to select one instrument and a historical date range, download its available one-minute candles, and prepare a replay.

**Why this priority**: Historical candle data is the required input for every replay.

**Independent Test**: Select one supported instrument and a date range with available data; verify the data preparation status, run account, and resulting replay coverage.

**Acceptance Scenarios**:

1. **Given** the user is in Backtest mode, **When** they request a run for one supported instrument and date range, **Then** the app creates one Backtest account and shows the current preparation stage with a percentage when measurable or indeterminate progress otherwise.
2. **Given** data preparation completes successfully with candles available, **When** the user opens the run, **Then** the run is ready and displays the covered date range.
3. **Given** the requested range contains dates with no candles or partial gaps, **When** data preparation completes, **Then** fully empty dates and summaries of partial gaps are reported and no artificial candles are added.
4. **Given** the entire requested range has no candles, **When** data preparation completes, **Then** the run and its Backtest account are deleted and a dismissible result remains on the run-list page with the instrument, selected range, and an action to edit the range.
5. **Given** data preparation fails, **When** the failure is reported, **Then** the failed run and its Backtest account are immediately deleted and a dismissible result remains on the run-list page with the instrument, selected range, and an action to start a new run.
6. **Given** data preparation is interrupted and the user retries it, **When** the retry completes, **Then** it continues the same run without creating a duplicate Backtest account.
7. **Given** historical data is refreshed after a run is ready, **When** the user reopens that run, **Then** it still uses the candle data selected when the run was prepared.
8. **Given** data preparation is interrupted, **When** the user returns to that run, **Then** it remains in preparation and can be retried without creating a duplicate Backtest account.
9. **Given** the user is entering a date range longer than one year, **When** they select or enter the end date, **Then** the form prevents accepting that range, explains the one-year maximum, and does not allow the run to be submitted.
10. **Given** the user starts a new run from the Backtest run-list page, **When** the run-creation form opens in manual mode, **Then** it asks for one instrument from the current catalog exposed by the pinned Dukascopy downloader, a start date, and an end date; the backend validates the submitted instrument against that catalog, and Dukascopy and one-minute candles are fixed for this version. Random and Blind mode behavior is defined by FR-023 and FR-039.
11. **Given** the user selects February 29 as the start date, **When** they select February 28 of the following year as the end date, **Then** the range is accepted; March 1 or later is rejected.
12. **Given** preparation is in progress, **When** the API backend restarts, **Then** the durable job continues or is reclaimed by the worker from its latest completed UTC-date checkpoint without creating another run or account.
13. **Given** one-minute data exists before the user's selected start date, **When** the run is prepared, **Then** the immutable snapshot also includes data from the preceding calendar month for chart history while the requested dates and the one-year limit continue to describe only the replay period.
14. **Given** some or all of the preceding month is unavailable, **When** preparation completes, **Then** it retains whatever warm-up candles are available and still becomes ready if the selected replay period contains candles; if the selected replay period has no candles, earlier warm-up candles alone do not make the run ready.

### User Story 3 - Replay candles interactively (Priority: P1)

As a trader, I want to play, pause, step through, and seek across completed candles so that I can inspect historical price action at my own pace.

**Why this priority**: Candle-by-candle replay is the core user experience in this version.

**Independent Test**: Start a ready run, step through several candles, use each playback control, and verify that the displayed candle and timestamp match the replay position.

**Acceptance Scenarios**:

1. **Given** the user is on the Backtest run-list page, **When** they select a ready run, **Then** its separate replay detail page opens.
2. **Given** a run is ready with available candles, **When** the user opens it for the first time, **Then** replay starts at the first available candle in the selected replay period, with earlier warm-up candles shown only as chart context.
3. **Given** a ready run is at a candle, **When** the user steps forward once, **Then** the replay advances by exactly one next available candle.
4. **Given** the replay is at a candle with a previous available candle, **When** the user steps backward once, **Then** the replay moves back exactly one available candle and hides all later candles.
5. **Given** replay is at the first available candle in the selected replay period, **When** the user steps backward, **Then** it remains at that candle and does not replay earlier warm-up context.
6. **Given** a ready run is playing, **When** the user pauses it, **Then** candle advancement stops at the current replay position.
7. **Given** the user has left a replay, **When** they return to that run after navigating away or reloading the app, **Then** it resumes at that run's last saved position.
8. **Given** the user selects a playback speed, **When** playback continues, **Then** 1x advances one candle per second, 5x advances five candles per second, and 20x advances twenty candles per second.
9. **Given** the user seeks to a historical timestamp, **When** the seek completes, **Then** replay moves to the first available candle at or after that timestamp within the selected replay period and is paused; a timestamp before the period clamps to its first available candle.
10. **Given** the replay is at a particular candle, **When** the chart is displayed, **Then** it does not reveal any later candle.
11. **Given** volume is available for a candle, **When** that candle is displayed, **Then** its volume is available for review.
12. **Given** a candle has a UTC timestamp, **When** it is displayed, **Then** the user sees the same instant in their configured timezone.
13. **Given** replay reaches the final available candle, **When** the user advances or continues playback, **Then** the run reports completion and does not advance beyond the selected data.
14. **Given** the selected chart timeframe is longer than one minute, **When** another one-minute source candle is replayed within the active chart interval, **Then** the active chart candle updates from the source candles seen so far and closes only after its interval is complete.
15. **Given** a ready run has warm-up candles before its selected start date, **When** the user opens it, **Then** those candles appear as historical chart context and the saved replay cursor starts at the first available candle in the selected replay period.
16. **Given** replay is at the first available candle in the selected period, **When** the user steps backward or seeks to a timestamp before that period, **Then** the replay remains at that first selected-period candle and does not treat warm-up candles as replayed candles.
15. **Given** the same replay data and chart interval, **When** the user changes the configured display timezone, **Then** the source candles remain grouped into the same UTC-aligned chart bars and only their displayed timestamps change.
16. **Given** a ready run is open, **When** the user adds chart tabs, **Then** each tab shows the same run's instrument and can use a different chart timeframe.
17. **Given** a run has multiple chart tabs open, **When** the user plays, pauses, steps, seeks, or changes playback speed, **Then** every tab reflects the same one-minute replay position and replay synchronization cannot be disabled.
18. **Given** a chart tab is open, **When** the user inspects or navigates its chart, **Then** crosshair inspection, panning, and zooming are available.
19. **Given** multiple chart tabs are open, **When** the user moves a crosshair, **Then** the other tabs synchronize it to the nearest available candle at or before the same UTC time.
20. **Given** a replay detail page opens, **When** the chart workspace appears, **Then** crosshair synchronization is enabled and no Chart sync section is shown; panning and zooming affect only the pane being navigated.
21. **Given** a chart tab has a valid interval selected, **When** the user enters a non-integer custom interval or a value outside 1 through 1,440 minutes, **Then** the form shows an inline error and keeps the tab's last valid interval.
22. **Given** a run has chart tabs with selected intervals, **When** the user navigates away or reloads and reopens that run, **Then** the tabs and their selected intervals are restored.
23. **Given** crosshair synchronization is enabled and the target timeframe has no candle at the source timestamp, **When** the crosshair is synchronized, **Then** the target uses the nearest available candle at or before that UTC timestamp, or shows no synchronized crosshair if no such candle exists.
24. **Given** the user pans or zooms one chart pane, **When** another chart tab is visible, **Then** the other pane keeps its own horizontal range.
25. **Given** a chart pane is first opened or remounted, **When** its replay-bounded data is ready, **Then** it is snapped to the latest candle revealed at the run's current replay position and follow mode is active.
26. **Given** a chart pane is following, **When** playback advances or the user steps or seeks forward or backward, **Then** the newest candle available at the selected replay position remains at the chart's real-time edge with its normal right-side spacing.
27. **Given** the user pans a pane earlier or later so the latest revealed candle is no longer at the real-time edge, **When** replay advances, **Then** that pane's selected time range is preserved, follow mode is inactive, and a return-to-latest button appears at the lower right of that pane.
28. **Given** a pane is away from the latest candle, **When** the user selects its return-to-latest button, double-clicks the time axis, or manually pans back to the real-time edge, **Then** that pane snaps to its latest revealed candle, follow mode becomes active, and the button is hidden.
29. **Given** the user pans one chart pane or selects its return-to-latest button, **When** other chart panes are open, **Then** only that pane's viewport and follow state change.
30. **Given** a higher-timeframe candle is updated by another source candle within the same interval, **When** the pane is following, **Then** its horizontal viewport does not jump or change scale solely because the active candle's values changed.
31. **Given** a pane is panned forward into space beyond the current replay cursor, **When** replay advances until the latest revealed candle reaches that pane's normal real-time edge, **Then** follow mode is considered active again and subsequent cursor advances keep it there.
32. **Given** a chart pane is open, **When** the user selects its timeframe, **Then** a compact, chart-styled dropdown is shown inside the upper-left of the plotting area with standard presets and Custom last.
33. **Given** the user selects Custom, **When** the custom-timeframe popup opens and they enter an integer number of minutes from 1 through 1,440, **Then** the pane uses that interval, persists it with the workspace, and displays the selected interval (for example, 7m) directly in the dropdown.
34. **Given** a replay workspace is open, **When** the user views its controls, **Then** the tab row contains an accessible `+` button and the chart has no redundant title, visible volume note, or standalone interval header.

### User Story 4 - Find a run through its Backtest account (Priority: P2)

As a trader, I want each replay run represented by an account in the Trades workspace so that I can identify and select a specific run.

**Why this priority**: It gives each run a familiar, unique place in JanusEdge while leaving later trade tracking possible.

**Independent Test**: Create two runs, view the Backtest account selector in Trades, and verify that each run has a distinct account and selecting one identifies only that run.

**Acceptance Scenarios**:

1. **Given** a non-blind Backtest run is created, **When** the user views Trades in Backtest mode, **Then** the run appears once as an account option labeled with its instrument and date range; a blind run's label includes the instrument and “blind” without dates.
2. **Given** two runs use the same instrument and date range, **When** the user views the Trades account selector, **Then** their labels have unique suffixes that distinguish the runs, including when blind labels omit their dates.
3. **Given** a Real account and a Backtest account have the same displayed name, **When** the user switches modes, **Then** those accounts remain distinct.
4. **Given** the user selects a Backtest account in Trades, **When** no trade-recording feature is available yet, **Then** the run can be identified and the trade list shows its empty state.

### User Story 5 - Annotate replay charts (Priority: P2)

As a trader, I want to annotate a replay chart so that I can retain observations for a particular run and timeframe.

**Why this priority**: Drawings let users record chart observations while preserving the run's replay and timeframe context.

**Independent Test**: Create, edit, and remove drawings on a replay chart, leave and reload the run, and inspect the saved drawing state at different replay positions and timeframes.

**Acceptance Scenarios**:

1. **Given** a replay chart tab is open, **When** the user uses the standard drawing tools, **Then** they can create, select, reposition, edit, and remove supported drawings.
2. **Given** the user changes a drawing, **When** they leave and later reopen the same run and timeframe, **Then** the drawing state, including edits and removals, is restored for that user.
3. **Given** a run has tabs with different timeframes, **When** the user switches between them, **Then** each timeframe retains its own drawing state.
4. **Given** the pinned CandleKit artifact provides replay-aware drawing visibility, **When** the replay cursor moves backward or forward, **Then** that behavior is preserved.
5. **Given** the pinned CandleKit artifact provides no replay-aware drawing visibility, **When** the cursor is before any of a drawing's time anchors, **Then** the drawing is hidden until all anchors are at or before the cursor. This fallback leaves saved state unchanged and does not use drawing creation or edit time.

### User Story 6 - Delete a run and its activity (Priority: P1)

As a trader, I want to permanently delete a Backtest run together with its dedicated account and trades so that the run and the activity it owns can be removed as one unit.

**Why this priority**: A run and its associated Backtest records form one user-owned unit; leaving its account or trades behind would create orphaned activity.

**Independent Test**: Delete a ready run that has associated trades and verify that the run, account, trades, and run-specific replay data are removed while another run and all Real data remain unchanged. Repeat with a preparing run and confirm it cannot become ready after deletion begins.

**Acceptance Scenarios**:

1. **Given** a preparing, ready, or completed run appears in the Backtest run list, **When** the user selects Delete, **Then** a confirmation identifies the instrument, date range, and dedicated account, and explains that the run, account, and all trades associated with that account will be permanently removed.
2. **Given** the confirmation is open, **When** the user cancels, **Then** the run, account, trades, and replay data remain available and unchanged.
3. **Given** the user confirms deletion, **When** cleanup is pending, **Then** the run is no longer playable and its account and trades are hidden from Backtest trade-facing views; the run list communicates that deletion is in progress.
4. **Given** a run has completed deletion, **When** the user refreshes the run list or Backtest Trades and checks its storage, **Then** the run and deletion marker, dedicated account, every linked trade and trade-owned dependent record/file, and every object under the run's MinIO prefix are physically removed; the MinIO prefix is empty. Merely hiding resources or returning an accepted response does not satisfy this scenario.
5. **Given** a run is preparing when deletion is confirmed, **When** the preparation worker processes or recovers the job, **Then** the run never becomes ready and all partial preparation data is removed.
6. **Given** a run is deleted, **When** another Backtest run or Real workspace has records with similar labels or instruments, **Then** those unrelated accounts and trades remain unchanged.
7. **Given** cleanup is interrupted or the same delete request is repeated, **When** the deletion worker resumes, **Then** cleanup completes idempotently without restoring the run or leaving run-owned records behind.

### User Story 7 - Select a random replay period (Priority: P1)

As a trader, I want a random replay period for a selected instrument and duration so I can review different historical market conditions without choosing dates manually.

**Why this priority**: Randomized date selection makes it practical to sample historical behavior while preserving the existing replay and data-coverage workflow.

**Independent Test**: Create a run in random mode with controlled candidate data. Verify the pending state and disabled date inputs, deterministic bounded sampling, account creation only after a candle-bearing start date is found, and normal preparation after selection.

**Acceptance Scenarios**:

1. **Given** the user opens New Run, **When** they choose random selection and a duration of 1, 3, 6, or 12 months, **Then** both manual date controls are disabled and the request includes `period_selection: "random"` and `period_months` without date fields. Manual selection continues to send its existing request unchanged.
2. **Given** a random request is accepted, **When** the worker has not found a usable start date, **Then** the run remains in `selecting_period`, shows its instrument and selection status, and has no selected dates or associated account.
3. **Given** the worker tries candidate dates, **When** a candidate has no COMB one-minute candles in the configured local day, **Then** it tries another eligible date in the same year up to ten distinct dates, then selects another untried eligible year. Provider errors are preparation failures and are not treated as empty days.
4. **Given** a candidate date has at least one candle, **When** the selection is committed, **Then** the inclusive period end is the day before adding the selected calendar duration with month-end clamping, the dates and one account using FR-009's label rules are persisted, and normal warm-up and preparation continue.
5. **Given** the worker restarts during random selection, **When** it reclaims the durable job, **Then** it resumes from the fixed cutoff and persisted year/date attempts without repeating completed empty probes as new attempts.
6. **Given** every eligible year has been exhausted without a candle-bearing candidate, **When** selection ends, **Then** the run, account, and job are cleaned up and a dismissible failure identifies the instrument and selected duration.
7. **Given** the user deletes a run while selection is active, **When** the worker resumes or its current probe returns, **Then** deletion fences selection and no account is created for the deleted run.
8. **Given** a candidate start day contains candles but later days in its period are empty or gapped, **When** normal preparation finishes, **Then** existing selected-period coverage and no-data behavior still apply; a start-day probe does not promise continuous period coverage.

### User Story 8 - Create and replay a blind run (Priority: P1)

As a trader, I want to replay a randomized period without seeing its calendar dates or raw prices so I can evaluate my decisions without those values biasing me.

**Why this priority**: Blind replay builds on random-period selection and presents the same market movement without revealing its absolute time or price.

**Independent Test**: Create a blind run with controlled candle data. Verify the form locks random selection, the run/account UI hides calendar dates, and all chart panes show weekday/time and normalized prices anchored at the first replay candle.

**Acceptance Scenarios**:

1. **Given** the user opens New Run, **When** they select Blind mode, **Then** random period selection is enabled and cannot be changed while Blind mode remains selected; the duration remains selectable and manual date controls stay disabled and omitted from the request. When Blind mode is cleared, the existing manual/random selection can be changed. Blind mode is unchecked by default, and requests without it preserve the existing manual and random request shapes.
2. **Given** a blind run is selecting, preparing, ready, or has produced a failure notice, **When** the user views its run-list row, replay detail, coverage, notice, or account selector, **Then** no complete calendar date or date range is rendered. Once its account exists, both its account name and display label include the instrument and “blind”, have a unique suffix when needed, and omit dates.
3. **Given** a blind run is ready, **When** the user inspects its replay detail or any chart pane, **Then** the current replay timestamp, intraday time labels, date ticks, and crosshair/tooltips use the configured display timezone and show weekday plus clock time without a calendar date, and every displayed chart price value uses the same normalized scale.
4. **Given** a blind run has replay-period candles, **When** its chart is initialized, **Then** the open of the first available candle at or after replay start is displayed as 100; every candle's OHLC, warm-up context, price labels, and drawings use the same `100 × P / referencePrice` mapping across intervals, seeks, and reloads.
5. **Given** the first replay candle's open is zero or non-finite, **When** the snapshot is finalized, **Then** the run does not become ready and the user receives a clear failure result. A negative open uses the specified formula, including its reversed normalized price direction.
6. **Given** a blind run has a closed simulated trade, **When** the user views it in Trades, the Journal, or an analytics view, **Then** its time is shown as weekday plus time in the configured display timezone, its displayed prices use the run's normalized reference, and no complete date or raw price is rendered.

### User Story 9 - Practice simulated trades during replay (Priority: P1)

As a trader, I want to place and manage simulated orders while historical candles replay so that I can practice discretionary decisions and review the resulting trades without sending orders to a broker.

**Why this priority**: Manual execution practice is the primary value of simulating trades in the existing replay.

**Independent Test**: Create a run with balance/risk settings, open a ready run, submit market and limit entries with both protective levels using auto or manual sizing, advance through controlled candles, verify independent chart indicators and drag/BE/X controls for multiple filled positions, then verify exact limit prices, pending orders, fills, Journal tags, original risk, closed trades, and account balance/analytics.

**Acceptance Scenarios**:

1. **Given** a ready run has revealed a one-minute candle, **When** the user submits a market entry preview anchored at the current close with both stop-loss and take-profit, **Then** the order remains pending until the next available one-minute candle, fills at that candle's open with the run's configured fill costs, and its protective orders become eligible only after that fill candle has been fully processed.
2. **Given** the user submits a limit entry after a candle is revealed, **When** later one-minute candles arrive, **Then** only those future candles can fill the order, a wick touch is sufficient, and a candle already revealed at submission cannot fill it retroactively.
3. **Given** a future candle opens through a submitted limit price and its high-low range later reaches that price, **When** the candle is processed, **Then** the limit entry or take-profit fills at exactly the submitted price. If the candle remains entirely beyond the limit and its range never reaches it, the order remains pending. A protective stop-market order still receives the worse opening price when the candle gaps through its stop.
4. **Given** an entry order is filled, **When** the position becomes active, **Then** its required stop-loss and required take-profit are linked OCO orders; if an eligible future candle touches both, the stop-loss fills first and the take-profit is canceled.
5. **Given** multiple positions or entry orders exist for the run's one instrument, **When** an opposite-side order fills, **Then** it reduces the oldest open exposure first, protection is reduced or canceled with that exposure, and any remaining quantity opens a separately protected position in the opposite direction.
6. **Given** an entry order is pending, **When** the user cancels it, **Then** it cannot fill on later candles. Open positions and working orders are restored from the run's saved simulation state after navigation or reload.
7. **Given** replay has advanced after a simulated order was submitted, **When** the user tries to seek or step backward, **Then** the system requires a confirmed simulation reset; reset clears that run's order and fill history, positions, recorded simulated trades, and simulation analytics, then returns replay to its first replay-period candle.
8. **Given** replay reaches its last replay-period candle, **When** the candle's orders have been processed, **Then** pending entry orders are canceled and every remaining position is closed at the final candle close using the run's configured fill costs.
9. **Given** an exposure is partially or fully closed, **When** the user views Trades or run analytics, **Then** only fully closed simulated trades appear in the run's dedicated account and the same applicable trade metrics available for Real accounts are available for that account.
10. **Given** the user opens a run's cost settings, **When** they enter spread, slippage, and commission values, **Then** the run saves and displays that profile; changes affect future fills while each existing fill retains the costs applied at execution. When all costs are unset or zero, the run clearly reports that costs were excluded and gross and net P&L are equal.
11. **Given** the user opens a ready run, **When** they choose Market or Limit in the collapsible entry panel beside the chart workspace, **Then** a chart preview shows the entry, stop-loss, and take-profit with long/short levels oriented correctly. The market entry is fixed at the current revealed candle close; a limit preview can be moved as a group, and either protective level can be moved independently. Place order is enabled only when both protective prices are set on the correct sides.
12. **Given** an entry order is filled and its position remains open, **When** the user manually closes that position, **Then** the system closes its remaining quantity at the current revealed candle close and cancels its linked stop-loss and take-profit orders as part of the same committed operation.
13. **Given** a user creates a run without overriding its risk fields, **When** the form is displayed, **Then** initial balance is USD 10,000 and risk is 1%; the order panel's auto-size checkbox is checked and calculates position size from the preview's stop distance, while unchecking it enables manual lot input.
14. **Given** an entry has filled and its position remains open, **When** the user moves its stop-loss or take-profit, **Then** the selected protection price changes for future candles, the original initial risk and R-based analytics basis remain unchanged, and moving the stop adds one `stop-moved` tag to the closed Journal trade in the user's General category. Moving only the target does not add this tag.
15. **Given** one or more simulated positions remain open, **When** the user views a chart pane in that run, **Then** each position has its own chart indicator set with a fixed side-labeled entry line and price, movable SL/TP lines with price labels, remaining quantity, and unrealized USD P&L at the latest revealed close before hypothetical exit costs. The indicators are derived from committed simulation state, are rendered on every chart pane in the run, and are not saved as user drawings.
16. **Given** an open position's chart indicators are visible, **When** the user drags its stop or target, selects BE, or selects X, **Then** only that position is affected. Dragging edits the selected protection under FR-053; BE requests a stop at that position's entry price under the same validation and next-candle activation rules; X closes that position's remaining quantity at the current revealed candle close and cancels its linked stop and target under FR-051. The entry line cannot be moved after fill.
17. **Given** multiple positions are open, including positions with overlapping indicator levels, **When** the user moves a protection, selects BE, or exits one position, **Then** the action is bound to the selected position and its own OCO orders, while every other position and its controls remain unchanged. BE is unavailable when the entry price has already been crossed by the current revealed close.

### Edge Cases

- The requested range includes dates with no candles or partial gaps within populated dates; gaps are reported and the replay advances through available candles without synthesizing bars.
- The month before the selected start may be fully available, partially available, or unavailable; missing warm-up candles do not block a run that has replay-period candles.
- The selected replay period has no candles while the preceding month does; warm-up candles alone do not make the run ready.
- The selected start is near the end of a month or crosses a daylight-saving boundary when the preceding calendar-month boundary is calculated.
- The requested range contains no candles at all.
- A random candidate is on a month end or leap day; month addition clamps before subtracting one day for the inclusive end.
- The random selection cutoff is captured near midnight in a non-UTC display timezone or a candidate local day crosses a daylight-saving boundary.
- A year has candles on dates not sampled by its ten probes; the bounded search discards that year and can report no usable start after all remaining years are exhausted.
- A provider failure occurs during a random probe; it is reported as a failure and does not count as an empty day.
- The worker restarts with a pending candidate probe, or the user deletes the run during that probe.
- Blind mode is enabled while the user changes period selection, or a blind run is shown in a list, notice, account selector, coverage view, chart axis, tooltip, or drawing.
- The first replay candle has a zero or non-finite open, or a negative open that reverses the direction of the normalized price scale.
- The user requests a date range longer than one year.
- Data preparation fails; the failed run and its account are immediately deleted after the user is shown an error.
- Data preparation is interrupted; the run remains in preparation and a retry must not duplicate its account.
- The API backend or preparation worker restarts while a run is preparing; the durable job and completed UTC-date checkpoints remain available for recovery.
- The supported-instrument catalog cannot be fetched; the app reports a service error and does not create a run or account.
- A seek timestamp falls in a gap or after the last available candle.
- The user steps backward at the first replay-period candle; replay remains there and does not enter warm-up context.
- Seeking while playback is running pauses the replay at the selected position.
- Playback reaches the last candle.
- A chart pane is panned earlier or into future whitespace while playback continues; the detached viewport must not be pulled back by replay updates.
- The user steps backward or seeks while following; the visible latest candle is the latest one at the new cursor, with later data still hidden.
- A pane is panned away from its latest candle; replay updates must preserve that pane's range without changing other panes.
- A source candle updates an existing higher-timeframe active bar; follow mode must not introduce horizontal jitter when no chart bar is added.
- A Real account and Backtest account share the same displayed name.
- Two Backtest runs use the same instrument and date range and need distinct account labels.
- The user changes workspace while data is downloading or replay is paused.
- Data is refreshed after a run is ready; the run must retain its original selection.
- A user confirms deletion while a preparation worker holds a live lease; deletion must fence publication and resume cleanup after interruption.
- A run has zero, one, or multiple account-associated trades when it is deleted; only trades linked to that run's dedicated account are removed.
- A run deletion is retried while cleanup is pending or after completion; it must not affect another run or Real account with a similar label.
- A market order submitted after a candle is revealed waits for the next available candle and fills at its open; no part of the already revealed candle can affect the fill.
- A pending limit is opened through but not reached by the eligible candle's high-low range, or an order is submitted at a price already crossed in the latest revealed candle; a limit fills exactly at its submitted price only when an eligible future candle's range reaches it, while protective stops use the adverse gap-open price and prior candle data cannot cause a new fill.
- A candle touches both an active stop-loss and take-profit, or opens beyond either one; the adverse stop-loss ordering and gap fill rules remain deterministic.
- The user modifies one or both protective prices after entry fill; the update must not inspect past candles, change original initial risk, or duplicate the `stop-moved` tag on a retry.
- An entry order fills at or during a candle whose later range also crosses its bracket; the bracket is not eligible until the next available candle after the fill candle has been fully processed.
- An opposite-side fill closes one FIFO trade, partially reduces another, or reverses beyond the available exposure; attached protection follows the remaining quantity.
- The user cancels an order, refreshes the page, restarts the backend, or submits an order while playback is advancing; order events remain ordered and are not duplicated.
- Replay reaches its last candle with pending orders, open positions, or an order that fills on that last candle.
- A closed forex trade has a non-USD quote currency and requires a historical quote-to-USD rate at the exit time.
- A simulated order or trade belongs to a blind run; displayed order levels, fill prices, trade prices, timestamps, and run metrics follow the blind presentation rules.
- Multiple open positions have overlapping chart indicator levels or one position's entry has already been crossed, so controls must remain bound to the selected position and an invalid BE action must be unavailable.
- The user attempts to step or seek backward after simulated state has been created, including after all open positions have closed.

## Requirements

### Functional Requirements

- **FR-001**: The app MUST provide separate Real and Backtest workspaces for each user.
- **FR-002**: Real mode MUST preserve existing Real trade, account, import, manual-entry, and journal behavior and MUST exclude Backtest runs, accounts, and activity from all trade-facing sections and reports.
- **FR-003**: Backtest mode MUST provide the existing applicable sections and a candle replay workspace; trade-facing sections MUST exclude Real trade records.
- **FR-004**: A Backtest run MUST use one instrument from the current supported-instrument catalog exposed by the pinned Dukascopy downloader dependency. The backend MUST validate the submitted code against that catalog before creating a run or account. The user-selected replay period MUST cover an inclusive range of historical calendar dates no longer than one calendar year in the user's configured display timezone. The end date MUST be earlier than the start date's one-year anniversary; for a February 29 start, that anniversary is March 1 of the following year, so the latest permitted end date is February 28. The selected local-day boundaries MUST be converted to UTC when defining the replay period. The one-year maximum applies to this selected replay period, not to the additional warm-up history.
- **FR-005**: The app MUST retrieve one-minute COMB BID/ASK candles for the selected instrument from one calendar month before the selected start date through the selected end date, and derive midpoint open, high, low, and close by taking the arithmetic mean of each corresponding BID/ASK field. The warm-up start date MUST be calculated in the configured display timezone by subtracting one calendar month from the selected local start date and clamping to the last valid day of the preceding month when necessary; both warm-up and replay boundaries MUST then be converted to UTC. The single candle `volume` value MUST be the sum of bid and ask quoted liquidity, and the chart MUST identify it accessibly as quoted liquidity rather than executed trade volume without requiring a persistent visible explanatory banner. Since the source provides independently aggregated side highs and lows rather than synchronized intraminute quotes, midpoint high and low are component-wise midpoint estimates, not exact tick-level midpoint extrema. Preparation MUST run through a durable worker backed by persisted jobs, independent of the HTTP request lifecycle. It MUST survive API backend restarts and recover interrupted jobs from the latest completed UTC-date checkpoint without duplicating the run or account. During preparation the app MUST show the current stage and a percentage when progress is measurable, or indeterminate progress otherwise; it MUST show a ready state when successful and a result message when no replay-period data is available or preparation fails.
- **FR-006**: A run MUST become ready only when data preparation completes successfully and at least one candle is available inside the user-selected replay period. Warm-up candles outside that period MUST NOT satisfy the readiness requirement.
- **FR-007**: The app MUST report requested replay-period dates with no candles and summarize partial gaps between available one-minute source candles within populated replay-period dates. It MUST NOT synthesize candles for gaps and MUST replay eligible candles in chronological order. Warm-up history MAY be incomplete or empty and MUST NOT cause a preparation failure when replay-period candles are available.
- **FR-008**: Each run MUST retain the exact candle selection used for its warm-up context and replay period so later data refreshes do not change that run's history.
- **FR-009**: Each run MUST have exactly one automatically created Backtest account, distinct from Real accounts, including when displayed names match. A non-blind account label MUST include the instrument and selected date range; runs with the same instrument and range MUST have a short unique suffix to distinguish them. For blind runs, both the stored account name and display label MUST include the instrument and the word “blind”, MUST omit all dates, and MUST have a short unique suffix when needed.
- **FR-010**: The Backtest account selector in Trades MUST identify its associated run; a run with no recorded trades MUST display an appropriate empty state.
- **FR-011**: When a run becomes ready, the app MUST persist its replay cursor at the index of the first available one-minute source candle in the user-selected replay period and that candle's timestamp as part of the ready-state update. This index MAY be greater than zero because the immutable snapshot can include warm-up candles. Users MUST be able to play, pause, resume, step forward or backward by one available replay-period source candle, and seek to a historical timestamp, subject to the simulation reset rule in FR-047. Stepping backward at the first replay-period candle MUST leave replay at that candle. Each run MUST retain its replay position across navigation and app reloads.
- **FR-012**: Playback MUST support 1x, 5x, and 20x speeds, defined as one, five, and twenty one-minute source candles per second respectively, regardless of the selected chart timeframe.
- **FR-013**: Seeking MUST position replay at the first available replay-period candle at or after the requested timestamp and MUST pause playback. A requested timestamp before the selected replay period MUST clamp to its first available candle. Seeking beyond available replay-period data MUST position the run at completion and leave playback paused. After any simulated order has been submitted, backward seeking or stepping MUST require the confirmed reset specified by FR-047.
- **FR-014**: The replay MUST display warm-up candles as historical chart context together with replay-period source data through the current one-minute replay position, and MUST NOT reveal later replay-period candles. Warm-up candles MUST NOT advance or change the replay cursor, playback progress, or completion boundary. When stepping backward, later replay-period source candles MUST be hidden again; stepping backward MUST NOT enter the warm-up interval.
- **FR-015**: Candle timestamps MUST retain their original UTC meaning and be displayed using the user's configured timezone. Blind charts MUST apply the weekday/time-only presentation specified by FR-039.
- **FR-016**: Dukascopy bid and ask quoted liquidity MUST be summed and available for review as quoted liquidity; the UI MUST NOT present it as executed trade volume.
- **FR-017**: No-data results and preparation failures MUST be reported in a dismissible run-list result that remains available after the run, account, and preparation job are deleted. Manual results MUST identify the instrument and range; random-selection results MUST identify the instrument and requested duration. A blind-run result MUST NOT render a complete calendar date or date range. A manual no-data result MUST offer an action to edit the range; random-selection exhaustion and preparation failures MUST offer an action to start a new run. Interrupted selection or preparation MUST remain pending, MUST NOT be shown as ready, and MUST offer a retry action. A worker restart or expired lease MUST NOT be treated as a terminal preparation failure.
- **FR-018**: Retrying or recovering data preparation for an interrupted run MUST continue the same durable job, run, and account. It MUST resume from the latest completed UTC-date checkpoint; an incomplete UTC date MAY be fetched again. Recovery MUST NOT create a duplicate run or account.
- **FR-019**: Trade import and Real-style manual trade creation MUST remain unavailable in Backtest mode. Simulated order entry and management MUST be available only within a ready run's replay detail as specified by FR-041 through FR-053; no Backtest action may submit a live order.
- **FR-021**: Backtest mode MUST provide a run-list page and a separate replay detail page. Selecting a ready or completed run MUST open its detail page, which identifies the run and presents a dockable chart workspace, replay controls, and the current replay timestamp.
- **FR-022**: The run-list page MUST show ready, completed, selecting-period, preparing, and deleting runs. Selecting-period runs MUST show their instrument and selection status without dates or an account label until a start date is found. Preparing runs MUST show the current stage and a percentage when measurable, or indeterminate progress otherwise; deleting runs MUST be identified as pending cleanup and MUST NOT open. The page MUST refresh the run list every five seconds while at least one run is selecting-period, preparing, or deleting and stop polling when none are. Selecting a pending run MUST leave the user on the run-list page. When selection or preparation fails or returns no candles, the app MUST show the result described in FR-017 and then immediately delete the run, any associated Backtest account, and its preparation job; failed and no-data runs MUST NOT be retained in the list. A blind run MUST NOT render its selected dates or range in any run-list state.
- **FR-023**: The run-list page MUST provide a New Run action that opens a form requiring one instrument from the current catalog exposed by the pinned Dukascopy downloader. Manual selection MUST continue to require a start date and end date, preserve its existing request shape, and prevent selecting or accepting dates beyond the one-year boundary defined in FR-004. Random selection MUST offer durations of 1, 3, 6, or 12 calendar months; while selected, both manual date controls MUST be disabled and omitted from the create request. The form MUST include an unchecked-by-default Blind mode checkbox. When checked, it MUST force random selection and prevent changing to manual until unchecked; the random duration remains selectable. When unchecked, users MAY choose manual or random selection. Requests without Blind mode MUST preserve existing manual and random wire shapes. The backend MUST validate the instrument against the same catalog before creating a run. Dukascopy and the one-minute source interval are fixed for this version; the account label is generated automatically after random dates are resolved. Each chart tab MUST provide a compact chart-styled timeframe dropdown containing 1m, 5m, 15m, 30m, 1h, 4h, and 1d presets, followed by a Custom option. Selecting Custom MUST open a popup that accepts an integer-minute interval from 1 through 1,440. A valid custom interval MUST become the selected dropdown label (for example, 7m) and persist per tab. A non-integer or out-of-range custom interval MUST show an inline error and leave the tab's last valid interval selected.
- **FR-024**: Chart bars MUST be aggregated from the one-minute source candles using the same fixed, UTC-aligned interval boundaries as JanusEdge's existing chart, independent of the configured display timezone. Each interval MUST include its start boundary and exclude its end boundary. Each bar MUST use the first source candle's open, the highest source high, the lowest source low, the last source candle's close, and the sum of source volume when available; its timestamp MUST identify the start of the interval. Each replayed source candle MUST update the active bar, which MUST remain in progress until its interval ends. Missing source candles MUST NOT be synthesized.
- **FR-025**: A replay detail page MUST provide a dockable workspace of chart tabs for the same run and instrument, with a separately selected timeframe for each chart tab and no fixed v1 maximum tab count. Users MUST be able to create chart tabs, reorder tabs within a tab group, move tabs between groups, split a pane by dropping a tab at one of its edges, resize split panes, and close tabs while at least one chart tab remains. An accessible `+` button in the tab row MUST create and activate a chart in the focused group; a separate workspace toolbar and tab-drag instruction row MUST NOT be shown. Splitting moves the same chart tab and MUST NOT duplicate its chart or replay state. A new run MUST start with one 1m chart pane. The per-run workspace MUST retain stable chart ids, intervals, split topology and orientation, pane sizes, tab order, and active tab in each group across navigation and reloads. All chart tabs MUST share the run's one-minute replay position and playback state for play, pause, step, seek, and speed changes. Replay synchronization MUST always be enabled and MUST NOT be user-disableable.
- **FR-026**: Every chart tab MUST support crosshair inspection, panning, and zooming.
- **FR-027**: Crosshair position MUST synchronize across chart tabs by default, using the nearest available target candle at or before the source UTC timestamp; if none exists, the target tab MUST show no synchronized crosshair. Horizontal panning and zooming MUST remain local to each pane. The replay detail page MUST NOT show a Chart sync section or controls for changing these behaviors. Replay-position synchronization MUST remain always enabled.
- **FR-028**: Each replay chart tab MUST provide the standard drawing tools for creating, selecting, repositioning, editing, and removing supported drawings.
- **FR-029**: Drawing state MUST be scoped to the authenticated user, run, and chart timeframe. Changes and removals MUST be saved and restored when the user navigates away from or reloads that run and timeframe.
- **FR-030**: Drawing visibility during replay MUST preserve any replay-aware visibility behavior provided by the pinned CandleKit artifact. If it provides no such behavior, a drawing MUST be hidden whenever any time anchor is later than the current replay cursor and MUST become visible again when the cursor reaches or passes all anchors. This fallback MUST NOT use drawing creation or edit time and MUST NOT change the saved drawing state.
- **FR-031**: The docked chart workspace MUST be stored per authenticated user and run through a versioned, revision-checked layout contract. Layout writes MUST retain at least one chart tab and MUST validate unique chart ids, supported chart panel types, and valid intervals. If a run has legacy flat chart-tab records but no saved layout, the first workspace load MUST preserve their ids and intervals in a visible dock layout; if no legacy tabs exist, it MUST create the single 1m pane defined in FR-025.
- **FR-032**: Each replay chart pane MUST begin at the latest candle revealed by the run's current replay cursor with follow mode active. While following, playback, forward/backward stepping, and seeking MUST keep that latest revealed candle at the pane's real-time edge while preserving the chart's normal right-side spacing. This behavior MUST use only cursor-bounded chart data and MUST NOT reveal a later candle.
- **FR-033**: Follow mode MUST be determined independently for each pane from its current horizontal viewport relative to the latest revealed candle. If horizontal navigation moves that candle away from the real-time edge, that pane MUST stop auto-scrolling and preserve its chosen range as replay advances. Follow MUST become active again as soon as the pane returns to or naturally catches up with its normal real-time offset. A lower-right return-to-latest button MUST be visible only while the pane is away from the latest candle; selecting it or double-clicking the time axis MUST snap that pane to the latest revealed candle, re-enable follow, and hide the button. Pan and zoom changes MUST affect only the pane the user navigates.

- **FR-034**: Chart panes MUST omit the redundant chart title, timeframe text, visible volume explanation, and standalone interval-number header. The compact timeframe dropdown defined in FR-023 MUST be overlaid inside the top-left of each chart's plotting area, and volume's quoted-liquidity meaning MUST remain available to assistive technology.
- **FR-035**: The Backtest run list MUST offer an authenticated user a Delete action for each selecting-period, preparing, ready, or completed run. Before deletion begins, the user MUST confirm that deletion is permanent and removes the run, its dedicated Backtest account if one has been created, every trade linked to that account, and run-owned preparation, candle-snapshot, replay, chart-workspace, drawing, and simulation data. Canceling confirmation MUST leave all of these resources unchanged. After confirmation, the run MUST become non-playable and its account and trades MUST be hidden from Backtest views while cleanup is pending; this temporary hiding MUST NOT count as completed deletion. Cleanup MUST physically delete the trade records and their owned dependent data, the account and run records, and every MinIO object under the run's storage prefix, including staged preparation data and the immutable snapshot. The deleting marker MUST be removed only after all run-owned resources are physically removed. Cleanup MUST be durable and idempotent across API or worker restarts; deleting a selecting-period or preparing run MUST prevent selection/preparation from creating an account or publishing it as ready. Completion MUST leave no run, account, trade, deletion marker, or run-owned MinIO object for that run, MUST remove only data owned by that run, and MUST NOT affect Real records or another Backtest run.
- **FR-036**: For each run, the system MUST request warm-up candles beginning one calendar month before the selected local start date. Month subtraction MUST use the configured display timezone and clamp to the final valid day in the preceding month (for example, March 31 subtracts to February 28 or 29). The user-selected dates, selected-period gap reporting, run/account labels, and one-year range validation MUST remain based on the replay period; the additional warm-up month MUST NOT change those values. Blind-mode rendered views MUST omit those dates even though the run retains them.
- **FR-037**: A ready run's immutable snapshot MUST include all available warm-up candles and all available candles within the selected replay period. The system MUST persist the first source-candle index whose UTC timestamp is at or after the selected replay start. On first open, that source candle MUST be the replay cursor while earlier snapshot candles are visible only as historical chart context. Missing or partial warm-up data MUST NOT block readiness when the replay period contains data; warm-up data alone MUST NOT make an otherwise empty replay period ready. Playback, stepping, seeking, replay progress, and completion MUST be bounded to the selected replay period, with seeks before its first available candle clamped to that candle.
- **FR-038**: Random period selection MUST accept `period_selection: "random"` and `period_months` equal to 1, 3, 6, or 12, while leaving the manual-date request shape unchanged. At request creation the backend MUST capture yesterday in the configured display timezone and persist that cutoff for the job's lifetime. Eligible local start dates MUST be from January 1, 2005 through the latest start whose clamped calendar-duration end (the day before adding the selected months) is on or before the captured cutoff. The worker MUST randomly try eligible years without replacement and, within each year, probe at most 10 distinct eligible dates without replacement. It MUST check COMB one-minute candles for each candidate's local calendar day using the same timezone-to-UTC boundaries as replay. An empty day MUST count as an empty probe; provider errors MUST be terminal errors, not empty results. After ten empty probes the year MUST be discarded and an untried year selected. A candle-bearing day MUST resolve the start date and inclusive end, persist those dates, create exactly one account using FR-009's label rules, and continue through normal warm-up and preparation. Until a start is found, the run MUST remain in `selecting_period` with null dates and no account, and the run list MUST show the instrument and selection status. If every eligible year is exhausted, the app MUST create a dismissible failure that identifies the instrument and duration, remove the run/job, and leave no account. Deletion MUST fence an in-progress selection. A successful start-day probe MUST NOT guarantee coverage later in the period; existing gap, empty-date, readiness, and warm-up rules continue to apply.
- **FR-039**: Blind mode MUST be an immutable per-run option that implies random period selection. The create request MAY include `blind_mode: true` only with `period_selection: "random"`; omitting the field MUST preserve existing manual and random request shapes, and explicit false MUST behave like omission. The run MUST persist and return its blind flag. Blind mode MUST NOT redact source dates or prices from storage or API responses, but rendered Backtest UI MUST NOT display a complete calendar date, date range, or raw price for that run. This prohibition includes run lists and details, coverage and failure notices, deletion dialogs, account labels/selectors, replay cursor timestamps, chart ticks, crosshair tooltips, price labels, and drawings. Blind account labels MUST include the instrument and “blind” and MUST omit dates. All displayed intraday times MUST use the configured display timezone; replay cursor timestamps, date-bearing axis ticks, and crosshair labels MUST show the local weekday name and clock time without a calendar date. Display all chart OHLC and price-coordinate values using `displayPrice(P) = 100 × P / referencePrice`, where `referencePrice` is the open of the first available replay-period candle at or after the selected replay start. Apply the same immutable reference to warm-up history, all chart intervals, and replay seeks. For negative references, transform open and close directly and order the transformed high/low as the maximum/minimum of the transformed raw high/low so candle ranges remain valid; the price direction still reverses. A zero or non-finite reference MUST prevent the run becoming ready and MUST produce a clear failure result.
- **FR-040**: Closed simulated trades linked to a blind run MUST retain canonical values; the Journal trade list MUST render their time as weekday plus time in the configured display timezone, render entry, exit, order, and drawing price values using the run's normalized price reference, and MUST NOT render complete dates or raw prices. The privacy mode MUST be derived from the associated run, not inferred from its account label.

- **FR-041**: An active, non-complete Backtest run MUST allow the user to submit buy/long and sell/short market or limit entry orders from its replay detail. Stop-market remains available only as the protective stop order type; stop-market entries and stop-limit orders are outside this version, as are automated strategies, live broker routing, leverage, and margin modeling. Lot quantities MUST use the run's frozen forex pip size, price precision, and contract size, with 100,000 base-currency units per standard lot when no pair-specific contract size overrides that default. When auto-sizing is disabled, users MUST enter lots in increments of 0.001 with a minimum of 0.001 lot. Every submitted entry MUST include both a stop-loss and a take-profit at valid prices on the correct sides of the entry. New entries MUST be unavailable after the replay is complete until simulation reset.
- **FR-042**: The backend MUST be authoritative for each run's replay cursor and simulated order processing. Simulation MUST consume only the immutable completed one-minute candles in chronological order, independent of the chart timeframe. A market order accepted after candle N is revealed MUST remain pending until the next available unrevealed one-minute candle is processed, then MUST fill at that candle's open with the configured execution costs applied. The fill MUST NOT use candle N's prices or the fill candle's high, low, or close. A newly submitted limit entry MUST NOT use any part of a candle already revealed when it was accepted; it becomes eligible on the next unrevealed candle. A future candle MUST trigger a limit entry or take-profit only when that candle's high-low range reaches the submitted limit price; opening through the limit without the candle range reaching it MUST NOT fill the order. When reached, every limit entry or take-profit MUST record a fill price exactly equal to its submitted limit price, including when the candle opens through it; limit orders MUST NOT receive gap price improvement. Protective stop-market orders MUST use the adverse opening price when a future candle gaps through their stop. The candle source is the run's midpoint OHLC with configured execution costs applied under FR-045 without changing the recorded limit fill price. V1 assumes a full fill at the determined price and does not model queue priority or partial liquidity fills.
- **FR-043**: An entry's required stop-loss MUST be a stop-market order and its required take-profit MUST be a limit order. Both MUST become active beginning with the next available one-minute candle after the candle containing the entry fill has been fully processed, and MUST be linked OCO. If one eligible candle touches both active OCO orders, the stop-loss MUST fill first and the take-profit MUST be canceled. Gap-open behavior MUST follow FR-042. When an opposite-side fill reduces existing exposure, the system MUST apply it to the oldest open simulated trade first, reduce that trade's remaining quantity and protective-order quantity, and cancel its protection when fully closed. Partial-close results MUST be retained with the still-open trade and included when that trade is fully closed. Any excess fill MUST open a separately protected position in the reverse direction using the submitted entry's stop and target. Same-direction entry fills MUST remain separately identifiable for FIFO closure and trade reporting.
- **FR-044**: The replay detail MUST show working orders, fills, open exposure, and each simulated trade's status and MUST allow the user to cancel a pending entry order and manually close an open position. A completed manual close MUST cancel that position's linked stop-loss and take-profit orders. Order actions and candle steps MUST be processed in one authoritative order so a refresh, retry, or duplicate request cannot create a second fill. The application MUST persist the run's pending and completed order events, fills, open positions, protective orders, and trade results so replay resumes with the same simulation state after navigation or backend restart.
- **FR-045**: Each run MUST let the user configure and review one cost profile containing the full bid/ask spread width in pips, slippage in pips per fill, and commission per lot per side; values MUST be nonnegative. On midpoint reference prices, buys MUST incur one half of the configured spread and sells the other half; slippage MUST be adverse for each fill. For market and protective stop-market fills, spread and slippage MAY adjust the effective fill price. For limit fills, the recorded fill price MUST remain the submitted order price under FR-042, and spread/slippage amounts MUST be applied separately to P&L. Each cost MUST affect the result exactly once and MUST NOT change the recorded limit fill price. Changes to the profile MUST apply to future fills, while each existing fill retains the costs applied at execution. Gross P&L MUST reflect spread and slippage costs before commission; net P&L MUST also subtract commission. Commission is assumed to be denominated in USD per lot per side to match the existing trade analytics currency. If the profile is unset or all values are zero, the replay MUST explicitly identify costs as excluded and MUST report equal gross and net P&L. The cost profile and applied per-fill costs MUST remain available with the run's trades and analytics.
- **FR-046**: Each simulated trade MUST preserve gross native P&L and its quote currency for forex instruments, use the configured pair-specific pip and contract conventions, and retain its USD-denominated analytics values. The system MUST resolve the historical USD-per-quote-currency-unit rate at each entry/exit for supported non-USD-quoted pairs; USD-quoted instruments MUST use a rate of 1. Initial risk MUST be calculated from the executed entry price, initial stop-loss, filled quantity, modeled execution costs, and historical quote-to-USD rate at entry. Before fill, projected risk MUST use the preview entry reference and the conversion rate available at order acceptance; after fill, actual initial risk MUST be recalculated using the executed entry and event-time conversion. A gap between preview and execution prices MAY cause actual risk to differ from projected risk. When auto-sizing is enabled, size MUST be calculated against projected risk and the run's USD risk budget; when manual sizing is selected, projected and actual risk MUST still be displayed and recorded. Each fully closed trade MUST be added once to the Backtest account for its run, and the account MUST support the same applicable trade analytics and reports available for a Real account. Current balance MUST equal initial USD balance plus the committed net cash effect of simulation fills, with realized P&L and each applied execution cost included once; partial exits MUST update it when committed, while unrealized P&L on open quantity MUST be excluded. Open simulated trades MUST NOT appear as closed Journal trades or closed-trade analytics.
- **FR-047**: The replay MUST persist simulated orders, fills, open positions, closed simulated trades, applied costs, and replay position per run in the existing MongoDB persistence. Once any simulated order has been submitted, backward seeking or stepping MUST be disabled until the user explicitly confirms a simulation reset. Reset MUST clear only the selected run's simulated orders and order/fill history, positions, simulated trade records, and simulation analytics, return its replay cursor to the first available replay-period candle, and make the run replayable again. A reset MUST NOT affect the run's candle snapshot, cost profile, workspace layout, drawings, other Backtest runs, or Real records.
- **FR-048**: Simulated trades MUST belong exclusively to their run's existing Backtest account and MUST appear in Trades and account-filtered analytics only after they are fully closed. All currently available Real-account metrics MUST be available for the Backtest account using its closed trades. For a blind run, all order, position, trade, and analytics UI MUST preserve FR-039's privacy rules: no complete calendar date or raw price may be rendered, all displayed price values MUST use the run's normalized reference, and user-visible order price inputs MUST use that same normalized scale.
- **FR-049**: When replay processes its final available one-minute candle, it MUST first evaluate eligible orders on that candle, then cancel any remaining working orders and close every remaining open simulated position at the final candle close with the configured execution costs. The run MUST become complete and retain the resulting closed trades and account analytics.
- **FR-050**: The ready-run replay detail MUST provide a collapsible entry panel to the right of the chart section with Market and Limit entry actions and long/short direction selection. Selecting an entry type MUST display a temporary bracket preview on the active chart, visually showing the entry, stop-loss, and take-profit with risk/reward shading and values, quantity, and risk summary. The preview MUST be separate from persisted user drawings. A new preview MUST initially anchor its entry to the current revealed candle close. Its initial stop distance in pips MUST equal the current USD risk budget divided by the instrument's USD pip value for one standard lot, using the instrument's frozen pip size and contract size and the latest completed quote-to-USD rate no later than the current candle close; USD-quoted instruments use a rate of 1. Convert that pip distance to a price offset using the instrument pip size. Its initial take-profit MUST be exactly 1R (a distance from entry equal to the stop distance). A limit preview MUST support dragging the complete bracket to move entry and both protection levels together, plus independent dragging of either protection level. A market preview's entry MUST remain fixed at the close of the current revealed candle while its stop and target remain independently movable; actual market execution MUST still follow FR-042. Long brackets MUST place the stop below and target above entry; short brackets MUST reverse those sides. The panel MUST contain an auto-size checkbox, checked by default; when enabled, it MUST calculate lots from the run's risk budget and the current entry-to-stop distance, including modeled costs, and recalculate the displayed lots when the entry or stop changes; when disabled, it MUST require manual lots while retaining the projected risk summary. The Place order action MUST remain unavailable until both prices are finite, instrument-precision-valid, and correctly positioned relative to the preview entry; canceling or changing the preview MUST NOT persist an order or chart drawing.
- **FR-051**: The replay detail MUST provide a manual close action for each open simulated position. A manual close MUST close its full remaining quantity at the close of the currently revealed cursor candle, without advancing replay, through the authoritative simulation operation gate. It MUST apply the current execution costs and historical currency conversion, and cancel the position's linked stop-loss and take-profit orders in the same committed operation. The close MUST produce the same closed-trade and analytics result as other simulated exits and MUST be idempotent across retries.
- **FR-052**: Run creation MUST include an initial balance in USD and a per-entry risk percentage of current balance, defaulting to USD 10,000 and 1%. Both values MUST be finite and positive, and risk percentage MUST be no greater than 100. They MUST be persisted immutably with the run and exposed in its Backtest account. The USD risk budget MUST equal current balance multiplied by risk percentage divided by 100. The initial stop distance in FR-050 MUST express that USD budget in pips using one standard lot's USD pip value. Auto-sizing MUST calculate lots so projected loss at the selected stop, including modeled fill costs and the applicable quote-to-USD rate, does not exceed the USD risk budget; lot size MUST be rounded down to the 0.001 increment. If minimum lot size would exceed the budget, the order MUST be blocked with a clear explanation. Manual sizing remains available through FR-050. Current balance MUST equal initial USD balance plus the committed net cash effect of simulation fills, with realized P&L and each applied execution cost included once; partial exits MUST update it when committed, while unrealized P&L on open quantity MUST be excluded. Reset MUST restore current balance to the initial balance and preserve the run's initial balance and risk percentage.
- **FR-053**: For an open simulated position, the user MUST be able to move its active stop-loss, take-profit, or both after entry fill. Each modification MUST use the simulation operation gate, preserve the OCO relationship and unmodified protection order, and become eligible no earlier than the next available unrevealed one-minute candle. A modification MUST NOT fill retroactively from the candle currently revealed or any earlier candle; reject a replacement level already crossed by the current revealed close. The position's original initial-risk amount and R-based analytics basis MUST remain unchanged after protection edits. When the stop-loss price actually changes, the user's `stop-moved` tag MUST be associated with the position and appear on its closed Trade in the Journal; changing only take-profit MUST NOT add that tag. Ensure a user-owned tag named `stop-moved` exists, creating it under the system General category if absent. Tag creation and association MUST be idempotent, and an open position MUST retain the tag until its closed Trade is created.
- **FR-054**: Every open simulated position MUST have its own chart indicator set on each chart pane in its run, derived from the latest committed simulation state and keyed by stable position id. Each set MUST show a fixed side-labeled entry line and price, current stop-loss and take-profit lines with `SL`/`TP` price labels, remaining quantity, and the open quantity's unrealized USD P&L marked to the latest revealed candle close, using the run's frozen instrument metadata and latest completed quote-to-USD rate no later than that close, before hypothetical exit costs. Unrealized P&L is display-only and MUST NOT change current balance or closed-trade analytics. Stop and target lines MUST be independently movable under FR-053; the filled entry line MUST NOT be movable. Position indicators MUST NOT be persisted as user drawings, MUST restore from simulation state after navigation or reload, and MUST disappear when the position closes. Blind-run prices MUST follow FR-039's normalized display rules.
- **FR-055**: Each open position's chart indicator set MUST offer independent `BE` and `X` controls. BE MUST request a stop-loss modification to exactly that position's entry price and MUST use FR-053's validation, operation gate, OCO, tag, and next-unrevealed-candle activation rules; it MUST be unavailable if the entry price has already been crossed by the current revealed close. X MUST close only that position's remaining quantity at the current revealed candle close, without advancing replay, and cancel its linked stop and target in the same committed operation as FR-051. When multiple positions are open, all drag and button actions MUST be scoped to the selected stable position id and MUST NOT change another position or its controls. Icon controls MUST have accessible names identifying their action and position.

### Key Entities

- **Workspace Mode**: The user's current Real or Backtest context, which determines which activity is shown.
- **Backtest Run**: One replay for one instrument and selected historical date range, with up to one calendar month of separately bounded chart-context history, selectable from the Backtest run-list page and opened in its own replay detail page, including its data coverage, replay position, and run-owned simulation state.
- **Backtest Preparation Job**: The durable worker job associated with a run, including its lease and completed UTC-date checkpoints.
- **Backtest Account**: The automatically created account-like grouping for exactly one run, visible in the Trades account selector and labeled with the instrument and date range for non-blind runs or the instrument and “blind” for blind runs, with a unique suffix when needed.
- **Candle Data Selection**: The immutable one-minute OHLC candles and optional volume retained for one run, including available warm-up context and the selected replay period.
- **Replay Chart Tab**: A chart view for a Backtest run's instrument with a stable id, its own selected timeframe, and the run's shared replay position. A chart tab belongs to one tab group in the saved dock layout.
- **Chart Workspace Layout**: A versioned, user- and run-scoped layout tree containing split panes, pane sizes, tab grouping/order, active tab per group, and the configuration for each chart tab.
- **Replay Drawing State**: The supported chart annotations belonging to one authenticated user, Backtest run, and chart timeframe.
- **Simulated Order and Fill**: A user-submitted market or limit entry within one run and its execution against an eligible future candle, including state, side, size, order price, fill price, costs, and event time.
- **Simulated Position and Trade**: A FIFO-managed exposure created by fills in one run, with its remaining size, required stop-loss and take-profit, realized results, a derived per-position chart indicator set while open, and a closed-trade record linked to that run's Backtest account.
- **Simulation Risk Budget**: Current USD balance multiplied by per-entry risk percentage divided by 100. The default stop distance expresses this USD budget as pips at one standard lot; enabled auto-sizing calculates the submitted lot quantity from the selected entry-to-stop distance and modeled costs.
- **Simulation Cost Profile**: The per-run spread, slippage, and commission settings applied to simulated fills and closed-trade results.
- **Run Deletion Request**: A confirmed, user-owned request to permanently remove a Backtest run and its exclusively associated account, trades, orders, fills, positions, preparation data, snapshot, replay state, workspace, and drawings; cleanup can remain pending until all run-owned resources are removed.

## Assumptions

- Replay advances through completed one-minute source candles. A higher-timeframe chart bar may remain in progress and update as each source candle is revealed; tick replay and developing one-minute source candles are out of scope.
- Each run contains one instrument and one-minute OHLC candles; volume is shown only when available.
- Selected calendar dates use the user's configured display timezone, with day boundaries converted to UTC; candle timestamps retain their UTC meaning and are displayed in that timezone.
- Warm-up history means one calendar month before the selected start date, calculated in the same display timezone with end-of-month clamping. It is chart-only context: it is visible before the initial replay cursor but is not part of the replay, and partial or absent warm-up data is acceptable.
- COMB midpoint OHLC is derived component-wise from the corresponding one-minute BID and ASK OHLC values. Its high and low are estimates from independently aggregated side extrema; the selected minute data cannot reconstruct exact tick-level midpoint extrema. Combined candle volume is summed bid/ask quoted liquidity, not trade volume.
- The configured display timezone changes how candle timestamps are presented but does not change which one-minute source candles belong to a higher-timeframe chart bar.
- Market closures and other no-candle dates are gaps, not failed data requests; no artificial candles are generated.
- Seeking into a gap selects the first available candle at or after the requested time; seeking beyond the data ends the run.
- Each run automatically receives one Backtest account. Simulated closed trades belong to that account; open simulated exposure remains in the replay's simulation state until closed.
- Deleting a run is permanent and requires explicit confirmation. The delete action applies to preparing, ready, and completed runs and removes any simulated trades linked to that run's one-to-one Backtest account.
- V1 drawing support uses the standard drawing tool set and stores independent state per authenticated user, run, and chart timeframe.
- Blind mode is unchecked by default and immutable after run creation. It is a rendered-UI privacy feature, not API-level redaction; raw values remain available to existing replay calculations and API consumers.
- A blind chart's reference is the first available replay-period candle's open, excluding warm-up. The formula is applied even for a negative reference; zero and non-finite references fail clearly before readiness.
- Simulated orders use the immutable run's one-minute midpoint candles as their reference prices; OHLC bars do not model queue position, partial fills, or the order of price movement inside a minute.
- The per-run commission amount is assumed to be USD per lot per side because existing trade fee and analytics fields are USD-denominated. Spread and slippage are entered in the instrument's configured pip units.
- Once a run has any simulated order history, moving its cursor backward requires confirmed reset so order state cannot be silently rewound independently of replay.

## Out of Scope for This Version

- Tick and order-book replay, developing one-minute source candles, queue priority, partial fills, and price-path reconstruction within a candle.
- Stop-market entries, stop-limit orders, trailing stops, leverage, and margin requirements.
- In-place modification of a submitted working entry order. A pending entry may be canceled and submitted again; its draft bracket remains editable before submission. Filled positions' active stop-loss and take-profit orders can be moved as specified in FR-053.
- Automated strategy execution, optimization, and live broker connectivity.
- Multiple instruments in one run.
